================================================================================
FLUXO ESPERADO AO EXECUTAR /go_charge
================================================================================

1. [NAVIGATING_TO_STAGING] Nav2 navega de (-3,-3) para (4.0, 2.97) odom via SLAM
2. [CENTERING] charging_manager coleta 2s de /detected_dock_pose, corrige Y lateral
3. [DOCKING] docking_server assume:
   - ArUco guia a distâncias maiores (setor ±30°, timeout 2.0s)
   - LiDAR assume quando ArUco some: centra lateralmente com setor ±60°, para a 5cm
4. [CHARGING] 15 segundos de carga (log "Charging... X/15 s")
5. [UNDOCKING] Robô recua para staging area
6. [RETURNING] Nav2 navega para (0.0, 0.0, yaw≈-135°)
7. [IDLE] Banner com comandos impresso — pronto para novo ciclo

================================================================================
O QUE AINDA FALTA / PENDÊNCIAS
================================================================================

[A] ROBÔ SE PERDE DURANTE NAVEGAÇÃO ← PRIORIDADE PRÓXIMA SESSÃO
    ─────────────────────────────────────────────────────────────
    SINTOMA: durante ou após a navegação o robô perde a posição real
    e age como se estivesse em lugar diferente de onde está fisicamente.

    CAUSAS PROVÁVEIS (em ordem de probabilidade):

    1. DERIVA DE ODOMETRIA (mais provável)
       - Toda navegação usa frame odom (sem correção de SLAM).
       - Rodas do robô (R=0.10m, sep=0.305m) acumulam erro de posição ao girar.
       - Na rota (-3,-3)→(1,0) o robô faz uma curva longa (~36° de virada).
       - Ao chegar em "odom(4,3)" o robô físico pode estar em outra posição.
       - SOLUÇÃO POSSÍVEL A: usar SLAM para corrigir a posição (modo híbrido:
         bt_navigator usa map frame MAS só depois do SLAM estabilizar, com
         retries no charging_manager caso o primeiro goal falhe).
       - SOLUÇÃO POSSÍVEL B: pre-construir mapa, usar AMCL para localização
         estável (map frame sem pulos de TF), navegar em map frame novamente.

    2. SLAM AINDA SALTANDO TF (jump back in time)
       - SLAM em modo mapping publica map→odom a 50Hz.
       - A cada 5s (map_update_interval) re-otimiza e pode gerar TF com
         timestamp passado, limpando o buffer.
       - Mesmo sem usar map frame na navegação, o salto afeta laser_frame→odom
         via: laser_frame→base_footprint→odom (odom_to_tf usa get_clock().now()
         então este segmento é estável), MAS pode afetar o slam_toolbox
         rejeitando scans ("Message Filter dropping: queue is full").
       - Scans descartados → costmap obstacle_layer sem atualização → robô
         navega "às cegas" por alguns segundos → perde trajetória correta.
       - SOLUÇÃO: aumentar map_update_interval (ex: 15s) para reduzir
         frequência dos saltos; ou desligar SLAM completamente
         (slam:=False no launch) enquanto testa navegação.

    3. COSTMAP SEM MAPA ESTÁTICO — OBSTÁCULOS INVISÍVEIS
       - O global_costmap usa apenas obstacle_layer (LiDAR atual).
       - A dock é marcada como obstáculo em odom≈(5,3) mas somente enquanto
         estiver no range do LiDAR.
       - Se o robô se afasta e a dock sai do raio LiDAR (>10m ← não é o caso),
         a dock some do costmap e o planner planeja passar por ela.
       - SOLUÇÃO: checar no RViz se a dock aparece como obstáculo no costmap
         durante toda a navegação (topic: /global_costmap/costmap).

    4. MISMATCH NA POSE DE RETORNO (home após undocking)
       - Após undocking o robô está perto de odom(4,3) mas pode ter sofrido
         drift de contato físico com a dock.
       - Navegar para odom(0,0) com odom já driftado = vai para lugar errado.
       - SOLUÇÃO: usar LiDAR ao chegar em "home" para confirmar posição,
         ou aceitar uma tolerância maior para o goal de retorno.

    DIAGNÓSTICO RÁPIDO:
       ros2 topic echo /odom --once         # posição odom atual
       ros2 topic echo /detected_dock_pose  # pose publicada pelo estimador
       ros2 topic echo /global_costmap/costmap_updates  # costmap sendo atualizado?
       rviz2 → add topic /global_costmap/costmap  # visualizar costmap

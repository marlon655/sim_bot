(charging_dock) somente com LiDAR (camera removida), bateria simulada e

ATENCAO -- LICOES APRENDIDAS (SESSAO 13)
================================================================================

- target_y do estimador NAO deve usar o Y detectado via LiDAR quando a dock e estatica:
  o LiDAR esta no robo (posicao variavel) -> o oy em odom reflete o offset Y do robo.
  SEMPRE usar um valor fixo (dock_y_odom) para a componente Y do target quando o
  dock esta em posicao conhecida e estatica em odom.

- external_detection_translation_y nao substitui dock_y_odom:
  o translation_y corrige apenas um bias constante; o bias real e proporcional ao
  erro de Y do robo no staging (variavel). dock_y_odom resolve o problema na raiz.

- k_delta alto (1.0+) com abordagem curta (~0.8 m) causa yaw residual no final:
  o controlador graceful tenta corrigir ΔY fazendo uma curva -> chega com yaw != 0.
  Com k_delta=0.3 e dock_y_odom correto (ΔY ≈ 0): abordagem quase linear, yaw final ≈ 0.

- Para biseccao eficiente de parametros numericos: usar ros2 param set em vez de
  rebuild + restart. Implementar add_on_set_parameters_callback no node alvo.

     PROBLEMA:
       Quando /go_charge chegava durante GOING_TO_TASK ou EXECUTING_TASK,
       callbacks ainda pendentes (timers + futures) disparavam apos mudanca
       de estado e iniciavam um SEGUNDO DockRobot concorrente.
       Com dois DockRobot competindo:
         - Approach cabia: robot ia pra frente, dava re, voltava pra frente
         - Segundo retorno ao dock ficava torto ou em loop infinito
         - Primeiro retorno (startup, sem tarefa previa) funcionava pois
           nao havia callbacks pendentes

     CORRECAO -- adicionados state guards em 5 callbacks:
       _task_nav_acc  : if state != GOING_TO_TASK: return
       _task_nav_res  : if state != GOING_TO_TASK: return   (ja existia)
       _patrol_wp_acc : if state != GOING_TO_TASK: return
       _patrol_wp_res : if state != GOING_TO_TASK: return   (ja existia)
       _finish_task   : if state != EXECUTING_TASK: return  <- BUG PRINCIPAL
       _undock_done   : if state != UNDOCKING: return       (ja existia)
       _dock_acc      : if state not in (DOCKING,RETURNING_HOME): return

     BUG PRINCIPAL era _finish_task:
       go_charge -> DOCKING. Timer de 2s disparava _finish_task (sem guard)
       -> _start_returning_home() -> segundo DockRobot concorrente
       -> chaos na abordagem = robo torto ou em loop

  3. [BUG FIX] _dock_res: removido check de alinhamento Y+yaw apos status=4

     HISTORIA:
       - Check y_err/yaw_err era do branch dock-carregamento (ambiente 1 m, sem drift)
       - Aplicado no mundo fabrica (12 m+) causava FALHA por drift de odom SLAM:
           robo FISICAMENTE correto no dock, mas odom reportava Y/yaw desviados
           -> check falha -> retry com navigate_to_staging_pose=True
           -> staging (12,0) esta ATRAS do robo ja em (12.7,0)
           -> graceful controller empurrava robo pra frente infinitamente
       - "Ta torto" era drift cosmético do SLAM no RViz, nao desalinhamento fisico

     SOLUCAO DEFINITIVA:
       - Removidos: DOCK_Y_ODOM, ALIGN_TOL_Y, ALIGN_TOL_YAW
       - DockRobot status=4 + docking_threshold=0.05m sao o unico criterio

  4. [REMOVIDO] DOCK_LOST_DIST check em _battery_tick

    tempo << tempo_de_abordagem (distancia_staging / v_linear_max = 0.875/0.15 = 5.8 s).

- docking_threshold pequeno demais (0.02 m) causa loop infinito de retentativas:
    Graceful controller com v_linear_min=0.05 m/s nao consegue precisao de 2 cm.
    Robot ultrapassa 2.1 cm -> isDocked() nunca dispara -> approach_timeout (45 s)
    -> DockRobot falha -> charging_manager retenta -> "andando infinitamente".
    Usar 0.05 m: compativel com v_linear_min=0.05 e frequencia 50 Hz.

- Zona cega do LiDAR e causa de colisao quando sem cache keepalive:
    LiDAR min_range=0.30 m; LiDAR esta 0.194 m a frente do base_link.
    Zona cega comeca quando face_dock < 0.30 + 0.194 = 0.494 m do base_link
    -> robo ainda a 0.494 - 0.252 = 24 cm da face.
    Sem cache: estimador para de publicar -> apos external_detection_timeout (2 s)
    docking server usa pose YAML [13.0, 0.0] -> robo vai para X=13.0 -> colisao!
    Solucao: _publish_cached() em cada early-return do _scan_cb (10 Hz keepalive).

- navigate_to_staging_pose=True com robo ja proximo do dock causa caos em retry:
    Em retry (apos DockRobot falhar), servidor manda robo ao staging (12.0)
    mesmo estando em (13.1, 0) — robô faz navegacao reversa, fica confuso.
    Solucao: navigate_to_staging_pose=False + charging_manager faz pre-alinhamento.

- Abordagem sem pre-alinhamento: graceful controller empurra dock lateralmente:
    Sem PRE_ALIGN: robo chega ao staging de qualquer direcao com yaw errado.
    Graceful controller corrige yaw + Y ao mesmo tempo durante os 0.93 m finais
    -> gera componente lateral que empurra a face do dock para alinhamento.
    Solucao: dois passos de Nav2 (PRE_ALIGN + STAGING) antes de DockRobot;
    robo chega com yaw≈0 e ΔY < 4 cm; graceful controller so corrige X.

- Formula de garantia de gap minimo >= 5 cm:
    stop_distance - robot_front_offset - docking_threshold >= 0.05
    Com robot_front=0.252 e threshold=0.05: stop_distance >= 0.352 m
    Usar 0.36 para margem: 0.36 - 0.252 - 0.05 = 0.058 m = 5.8 cm OK.
